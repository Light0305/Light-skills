# 从代码到有效的一次运行

## 实现与预检

先定位项目说明、真实入口、配置系统、依赖文件、数据读取与评价代码。已有配置框架输出实际解析值（含默认值和命令覆盖）；保留实验真正使用的配置，不只复制最初输入。命令以参数数组表示，带空格路径分别传参；需要管道时写成已审查的项目脚本。

对关键方法建立有判别力的检查：

- ML：小样本过拟合或已知标签检查、各条件开关是否生效、训练/评价分离、正确的 split 计数。
- 数值：解析/制造解、误差阶、单位与边界条件、守恒/残差、参考实现；检查精度/截断误差而非只看退出码。
- 算法：穷举小实例对照、约束有效性、复杂度趋势、不可行/退化输入。
- 系统：工作负载真实执行、结果正确性、计时范围、预热与同步、共享资源竞争。

只加能检测真实错误的检查，不为低风险文案或记录模板写测试。占位输出用于开发时显式标注为 synthetic/mock，正式结果不得复用。

运行预检记录实际解释器/二进制、必要库与编译器、加速器/驱动、线程、精度和算法确定性设置、空闲资源、输入权限、输出空间。Python `pip freeze` 不是编译器、CUDA、系统 BLAS 和 GPU 驱动的完整替代。无 Git 项目可冻结实际源文件和依赖清单，不强制建仓库；有未提交代码时保存相关文件/补丁，不能只记 HEAD。

计时一个真实小运行，区分启动/编译、数据准备、计算、评价、写盘。基于实测给剩余时间范围及内存上限；超出能力时缩小 pilot 或选择可用资源，不偷偷替换正式问题。

## 运行矩阵与限额

计划至少记录 `experiment/task / condition / unit_id / seed或实例轴 / 输入与配置 / 预期输出 / 验收 / 状态 / actual_run_ids`。可用已有作业表、CSV 或 JSON；不强制固定文件名。分配表既是覆盖检查，也是防止只保留最好结果的依据。

每轮明确：最多多少次尝试、总墙钟或计算资源、单次时限、共享设备并发、诊断/重试余量、下一步触发条件。值来自任务/设计和实际资源；不要普遍规定“3 次重试”“3 个种子”或“5 分钟训练”。调参与修复消耗同一份投入账。技术重试可重复同一科学单位，但所有尝试仍保留。

不要把硬件容量当作已经获得资源。已知有长训练时使用项目已有调度器/持久任务；附带 local runner 是单机顺序命令记录器，不是集群编排平台。

## 故障分类、修复与续跑

| 信号 | 先看什么 | 有效动作 |
|---|---|---|
| import/编译/入口错误 | 当前解释器、依赖版本、真实路径、编译日志 | 最小修复后重做端到端检查 |
| OOM/超配/超时 | 峰值、批量、并发、实际耗时、时限 | 明确资源或规模变化；涉及数值/公平性时匹配基线 |
| 空指标/空数据/产物缺失 | 样本数、实际分支、输出路径、评价调用 | 修复链路，旧运行保留技术无效状态 |
| NaN/Inf、残差不降、守恒失败 | 输入范围、精度、步长、梯度/残差原始轨迹 | 区分算法失稳与代码问题；不直接删异常实例 |
| 所有条件结果完全相同 | 配置解析、开关、缓存键、被调用代码 | 核对实际参数与执行路径，排除参数未生效/旧缓存 |
| 指标异常好 | 泄漏、重复、测试集用于选择、评价被修改 | 冻结并诊断；重新评价要标明哪些证据作废 |
| 有效结果没有提升 | 质量检查与预设比较 | 记录负结果；不按“修 bug”无限调到显著 |

每次修复前保留错误全文、相关片段与失败产物；写清原因是已证实还是推测、改了什么、如何验证。除非实验正是研究组合更改，否则避免一次修复混入多个无法区分的科学变化。

恢复前先查实际 job/process 是否仍在运行，避免重复提交。记录检查点来源、哈希、训练步数、优化器/调度器/RNG 状态，以及续跑是否完整恢复。只有权重没有 RNG/优化器状态时，称 warm start，不声称与未中断训练等价。调度器任务取消要确认目标 job ID，不能根据模糊进程名批量终止。

local runner 被强制终止时可能留下 `started.json`、部分日志和锁。先确认该 runner 及其子进程都已停止，再由操作者移除该工作区的 `.operation.lock`（若存在），执行 `recover --reason ...` 标记中断并封存。`recover` 本身不终止进程、不续跑，也不证明任务已经停止；新尝试用新 ID。

## 一轮结束时

先列实际覆盖和质量结果，再给指定比较与有限解释。通过、不通过和未知分开。选择下轮运行基于尚待区分的解释、剩余预算和原先规则；若是探索性选优，保留搜索过程并安排设计要求的独立确认，不能拿同一验证集选出的赢家充当独立证据。
