# Light Patent

## 项目目录与续作

需要落盘或继续已有项目时，先读 [项目目录约定](references/project-layout.md)，按其中的本阶段位置、版本与关联规则保存；用户指定路径和旧项目优先。包内资源相对本 skill，研究产物相对真实项目，二者不要混用。只做局部讨论时无需初始化目录。

持续项目先恢复有关 Memory / Workflow，再回读本轮实际采用的论文、代码、实验或原申请文件；
记忆与台账不替代披露证据。与同源论文、软件、审查和更正的衔接见
[项目接入与回传](references/project-integration.md)。专利按需求接入，不是每篇论文的必经步骤。

把真实技术材料转化为保护范围有依据、实施细节可复核的专利草稿。默认中文、中国发明专利；用户指定的任务、法域、模板、语言与文件格式优先。独立完成当前授权的撰写工作，不把交底书确认、固定模型、外部服务或多智能体设置成默认前置条件。

## 选择当前任务

先利用已有文件和上下文识别交付物、技术类型、申请阶段、公开状态。只追问会改变技术方案、保护主题或修改边界的缺失事实，继续完成不依赖答案的部分。只改一句话时直接修改，不启动全案流程。

| 用户要做什么 | 按需阅读 | 交付重点 |
|---|---|---|
| 从论文、代码、想法中找专利点 | [材料与证据](references/intake-evidence.md)、[技术类型](references/technical-domains.md) | 候选方案、证据、差异假设、关键缺口 |
| 查新、判断与已有技术的区别 | [检索与对比](references/prior-art.md) | 实际检索记录、文献核验、逐特征对照及边界 |
| 写技术交底书 | [交底与说明书](references/drafting.md)，需要时读技术类型 | 可实施的技术主线、实施例、保护点、独立问题清单 |
| 写权利要求或完整申请草稿 | [权利要求](references/claims.md)、交底与说明书、技术类型 | 先定保护主线，再写权要、说明书、附图、摘要 |
| 修改、合稿、审稿或答复审查意见 | [修订与答复](references/revision-response.md)，涉及权要再读权利要求 | 最小必要修改、依据、影响、版本与未解决项 |
| 输出 Word、处理公式和附图 | [交付与导出](references/delivery.md) | 干净正文、独立文件、可编辑公式、实际图件与版式检查 |
| 涉及法律标准、公开日期、法域、提交要求 | [法域与官方依据](references/jurisdictions.md) | 核对当前官方文本、适用条件和生效时间 |

不默认加载全部参考文件。模板在 [assets/templates](assets/templates/disclosure.md)，工具数据结构见 [case-format](references/case-format.md)。工具用法和能力边界见交付与导出；仓库借鉴记录见 [来源评述](references/source-notes.md)。

## 贯穿整个任务的约束

1. **事实先于措辞。** 把源文件、定位、技术特征、说明书位置和权要限定关联起来。区分明确披露、必然推导、待确认、无支持；“常见”“合理”“可能”不等于必然。未披露的机制、范围、实验数据或变型不能因为能写得通顺就成为本发明内容。背景/对比文献不充当本发明披露；原申请依据具体定位到原说明书、权要或附图，单有角色标签不证明支持。
2. **保护技术关系。** 围绕问题、协同手段、输出及效果形成可实施的方案。通过删除测试判断必要特征；独权不漏核心协作关系，也不自动塞入品牌、优选数值或全部实验设置。权利要求数量与类别由材料和保护对象决定。
3. **检索不等于文字查重。** 新颖性逐份文献核对整个特征组合及关系；创造性另行分析区别、实际技术问题和结合启示。相似度、同义替换或自评分不能代替判断。检索未命中只能说明本次检索范围内的情况。
4. **尊重申请阶段。** 首次申请前可整理真实补充披露；已提交申请的修改以原始申请文件为边界，新的实验、代码版本或发明人补充不能自动成为原始依据。详细规则在修订与答复中。
5. **把不确定性放对地方。** 关键特征缺失就交付有价值的可支持部分和精确问题，不把占位符或推测混进正式权要。普通行政信息缺失不阻断技术撰写；不推定申请人、发明人、权属或优先权。论文作者名单不等于发明人名单。
6. **正文与工作记录分开。** 正式正文不含提示词、skill 名称、来源 ID、自检评分或检索失败日志。证据表、检索报告、修改对照、确认事项单独保存。

## 从材料到草稿

完整新案通常沿以下次序推进；窄任务复用已有可信成果，仅补做受影响环节。

- 阅读核心材料和图式，建立稳定定位，识别公开时间线、术语、公式、数据流或部件关系。先写出材料实际支持的技术方案，再提出可选发明点。
- 为选定主线形成“技术问题 → 相互配合的必要手段 → 技术输出/效果”，记录必要性理由、可选限定、可替换方案及证据缺口。不要为了凑多个专利而拆散协同机制。
- 当查新、授权风险或完整新案权要在范围内时，进行适量的当前公开检索；用户明确免检或已有充分检索资料时按其范围处理。窄幅润色无需重跑。不可联网则记录限制，继续可支持的草稿。
- 写独立权利要求，再设计有真实依据的从属退路；每个新增限定都关联源材料和说明书。根据权要补齐实施说明、公式解释、图件及摘要。交底书任务不强制生成正式权要。
- 分别检查源材料支持、充分公开、权要范围与引用、技术关系、术语/公式/附图一致性和现有技术差异。自动工具只检查结构；实际语义由逐项阅读判断。
- 交付用户要求的文件和简短状态：完成什么、关键依据、未解决的具体事实或检查限制。结果是供复核的撰写草稿；不声称授权保证、法律鉴定或已完成提交。

## 工具只在有收益时使用

长案、多文件或多轮修改可用结构化案件文件；短问题不要求初始化项目。

```text
python <skill目录>/scripts/init_case.py --title "一种技术方案" --out <案件目录>
python <skill目录>/scripts/audit_case.py <案件目录>/case.json --profile application --out <检查报告.json>
python <skill目录>/scripts/export_case.py <案件目录>/case.json --kind application --format both --out <新交付目录>
python <skill目录>/scripts/export_case.py <案件目录>/case.json --out <已有交付目录> --verify
```

初始化与审计只需 Python 3.10+ 标准库；Word 导出可选依赖见 `requirements-docx.txt`。初始化不复制或上传技术材料，导出不覆盖旧交付目录。不运行参考仓库的安装程序，不依赖本机参考仓库或其他 skill 才能完成核心撰写。没有导出工具时仍可交付完整正文与图源，并如实说明格式未完成。
