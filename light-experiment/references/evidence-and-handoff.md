# 原始证据、更正与分析交接

## 本轮开始前

已有 Memory 时恢复当前设计、执行范围、真实运行状态、剩余预算和未决故障，再读取相应 campaign、冻结设计、spec、日志、result、assessment。记忆中“跑完”“通过”可能只指进程退出，必须核对具体含义。已有 Workflow 时保留任务身份与验收；直接处理单个运行无需先启动总控。

读取 Design 的直接来源检查结果及方案正文，确认当前引用的科学依据。init 只冻结 context/design/plan/protocols，不自动检查上游证据蕴含，也不收集外部文献/数据。实际影响计算的数据、划分、评价器、代码和配置仍列入每次 run spec；大数据使用可核实版本和清单，不自动整库复制。

## 结果被更正以后

1. 读真实问题和原始证据，区分技术无效、有效阴性、科学解释改变和未知。有效阴性保留 passed QC；不能为丢弃不利结果而改成技术失败。
2. 用 assess 追加当前 QC 与判定，更正连接旧评估；保留旧 receipt、原始 result 和日志。只写 note 不会自动改变 QC。
3. 查直接和间接 depends_on_runs。新启动及下游 passed QC 都要求前置当前有效；verify 也会检查已消费的依赖，原始运行保持。
4. 前置由 passed 改成 failed/unknown/pending 时，依赖结果待复核，不能继续作为已通过证据。若前置仍为 passed 但评估版本改变，核对改变是否影响具体下游用途；工具提示复核，不自动认定重做科学实验。
5. 在 execution-report 与项目记忆记录受影响运行、具体更正和下一步。代码修复后新 run；方案改变新设计版本和 campaign。科学前提被推翻时回到 Idea/Literature，缺数据时再按需采集。

新运行在 started.json.dependencies 保存采用的前置 result/assessment 指纹。旧记录未含此字段时不伪造历史绑定，报告中标明实际可恢复范围。

已记录尝试或评估文件丢失时，从真实备份恢复并检查；不要删除事件、重置额度或补造“当时已通过”的记录。更正链和事件核对用于发现不一致，本机文件不构成可信时间或不可篡改证明。

## 交给 light-anaysis

先运行执行端 verify，处理错误并逐项解释与本轮分析有关的警告。ok=true 只表示记录完整性，不代表所有运行通过或足以支持主张。保留失败、未跑、未完成、排除和有效阴性，以及各自理由。

宿主检查运行矩阵覆盖、测量单位、独立单位、重试/重复、实际配置、数值有效性和原始逐单位值。读取指标 locator，核对实际值及其派生过程。文件存在或非空不能替代该步骤。

沿用实际分析入口，不构造另一个非原生交接 JSON：

```powershell
python "<experiment-skill-root>/scripts/experiment.py" verify --workspace "<execution-workspace>"
python "<analysis-skill-root>/scripts/analysis_bridge.py" ingest --execution "<execution-workspace>" --input "<actual-raw-file>" --out "<project>/Analysis/AN-0001_分析短名"
```

多个原始文件重复 --input；可重复 --execution 接受多批次，但仍是一项核心研究中的相关实验。已有外部数据直接用分析入口的 --input 接入，不伪造本地运行过程。

当前分析导入会收集设计、campaign、运行元数据和评估，**不会重新核验执行封存清单，也不会自动导入所有原始输出与日志**。显式提供所需原始值/日志及其数据字典。执行报告补充未测资源、已看结果后的改变、未完成项与影响。分析接收身份和观测，重新判断效应、不确定性、竞争解释；不要把本阶段 support/falsify 直接当论文结论。

## Memory 与 Leader 的增量

先把事实记在原生运行和报告，再由宿主写入有来源的记忆：设计/版本和本轮范围、实际运行/任务身份、三层状态、预算消耗与未知、关键阴性/故障、更正及受影响依赖、下一步与触发条件。长日志和全部指标仍留在专业目录，Memory 用定位与指纹引用。

向总控回交实际完成范围、证据路径、验收与剩余阻塞；范围不足或仍在运行时如实报告。更正影响已有 Memory/Workflow 判断时更新或标为待复核，不能只记新结论而让旧的“可用结果”继续生效。没有记忆工具时交付这些有来源的增量，不阻断当前专业工作。
