# 从项目形成软件理解

## 阅读顺序与输出

先辨认交付形态和本次版本，再读关键路径，不先发一张几十项的表单让用户代替分析。
可先查看 README/已有产品文档、依赖与启动配置、入口、一个典型流程、输出和错误处理。
科研仓库另读研究脚本、参数入口、环境文件、数据流、测试和复现说明。

写一段软件定位，列目标使用者、解决的具体任务、输入、核心处理、输出、适用边界。
再为每项拟写功能登记 `case.json.features`：

```json
{
  "id": "F01",
  "name": "批量导入实验记录",
  "status": "implemented",
  "evidence": [{"path": "src/importer.py", "lines": [18, 94], "note": "读取 CSV 并校验列名"}],
  "manual_heading": "导入实验记录",
  "limitations": ["不接受缺少 sample_id 列的文件"]
}
```

该片段是结构示例，不是待申报软件的事实。证据读取后可补 SHA-256，避免版本变动后复用旧结论。
`documented_only`、`planned` 和 `unverified` 不能在正式材料中写成运行验证通过。
源码支持只能证明实现线索，不能自动证明部署可用、性能达标或所有异常都已测试。

## 按形态理解，不把网页模板套在所有软件上

| 形态 | 优先查看 | 常见误判 |
|---|---|---|
| Web/桌面/移动端 | 实际页面、导航、事件处理、服务端业务、权限和结果 | 看到登录组件就宣称有完整账号体系 |
| CLI/批处理 | help、参数解析、文件校验、结果写入、退出码 | 捏造菜单/按钮，遗漏运行路径和输入要求 |
| 库/SDK/API | 公共接口、调用约定、序列化、错误模型、测试 | 把接口返回当成用户操作界面 |
| 科研分析程序 | 输入数据结构、预处理、核心计算、参数、输出与随机性 | 把论文实验结论当成软件功能或性能保证 |
| Notebook | 代码单元顺序、外部模块、运行依赖、可复现入口 | 把输出图片、数据、Markdown 都计入源程序量 |
| 嵌入式/控制程序 | 主循环、状态机、输入输出、硬件接口、异常路径 | 用开发电脑配置充当设备运行要求 |

运行只做授权范围内的轻量验证。没有运行条件时，写“根据源码/现有说明整理，运行尚未复核”，
不制造日志。可以用自建无敏感数据演示小输入，但应标注样例数据，不能冒充真实业务记录。

## 范围与来源

一个仓库可以含多个独立软件；一个软件也可以跨多个模块。按这次登记对象划界，不能只按
目录体积或前端占比选取。算法、前后端、数据处理、设备控制等真正实现应按实际功能覆盖。

确认自有实现、外部依赖、开源改编、模板、自动生成文件和 AI 辅助开发的边界。许可证存在
不等于申请人拥有上游著作权；保留第三方声明与来源，不自动改写包名、作者或版权信息。
合作、委托、职务开发、学校/单位任务和受让情况依用户事实与协议记录，Agent 不作权属裁定。

扫描器以已知后缀提供候选提示，同时保留未知文本和 Notebook 待审项。文档、配置、测试也可
成为理解证据；默认不算作程序正文，不代表一律没有著作权。对于 SQL、DSL、模板、低代码定义、
脚本式配置等，阅读内容后决定是否属于实际程序表达。被忽略、大文件、符号链接和编码失败项
都要复核；Git 忽略规则用于提示，不是“必定与软件无关”的证明。

## 完成标准

申请字段、手册核心功能、底稿中的实现与证据表能互相对应。既有材料与源码不一致时记录冲突，
有依据的最新用户事实可修正口径；不能简单以 README 或某个时间最新的文件压倒所有证据。
信息不足时仍交付已有理解、可编辑草稿和具体缺口，不把“等待全部资料”作为停止分析的理由。
