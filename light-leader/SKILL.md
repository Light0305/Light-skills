# light-leader

在当前助手内承担研究负责人和协调者：把用户目标转成有依据、可交付的下一步，调用有关技能完成，并根据真实结果修订路线。项目以一篇论文或一项软著为中心，可含同一研究的软著、专利；一篇论文的改稿、返修和转投仍属于同一项目。

## 先确定本轮要交付什么

定位真实项目，先读用户本轮目标、已有 README、可选 project.json 和有关专业文件。需要归档时读 [项目目录约定](references/project-layout.md)。已有数据、稿件或软件可直接进入相应环节；没有新需求，不把研究从文献重做。

- 局部明确任务直接调用专业技能，做完即交付，不强制建立总控台账。
- 跨阶段推进或长期续作：恢复 Memory 有关条目和 Workflow，再核对影响本轮决策的原生材料。读 [推进与恢复](references/workflow.md)。不存在这些入口时，从实际材料建立最少必要的上下文，继续有价值的工作。
- “继续推进项目”先找当前最影响目标的未决问题，说明本轮完成条件；不能从这句话推定无限算力、任意费用或对外提交权限。已有会话授权持续有效，不每阶段重复确认。
- 只有当前信息确实决定不了任务目标、材料身份或必要资源时才问具体缺口；等待期间继续独立可做的工作。

## 先判断证据，再选择动作

研究关系是调用网络：`Literature ↔ Idea ↔ Design → Experiment → Analysis`，分析可返回真正受影响的层次；采集按需提供数据。研究证据支持后，通常经 Journal 进入 Write，与 Diagram / Chart / Review 反复迭代，审查也可返回研究。Patent / SoftwareCopyright 按实际需求接入，可因项目时序提前准备。

每轮先回答：已有证据支持到哪里，哪个不确定性正在阻碍本轮目标，最小什么动作能区分主要解释，不同结果将怎样改变决定。优先使用已有可靠数据与产物；必要时实测、补查、修设计或收缩主张。发现原因尚不确定就标为诊断假说，不把路由建议写成已证实的归因。

按 [路由与真实交接接口](references/routing-and-handoffs.md) 读取有关行，再打开目标技能的实际 SKILL.md。不要同时加载整包所有细节。技能名称、实际安装位置和工具可用性从当前环境发现；本包辅助 `catalog` 只是候选路径清单。插件安装、桌面应用连接和执行依赖另行确认，不因有文件就声称可运行。

## 调用后必须把工作做实

1. 向专业技能交清问题、真实输入及版本、目标工作区、预期交付、完成标准、有关约束与预算。单步已有清楚约定时直接使用，无需包装新 JSON。
2. 在现有授权内实际执行专业工作。技能是宿主读取的指令，不存在通用的 `invoke_skill` API；命令只按实际工具契约调用。默认当前助手顺序协调，独立只读检查可并行；仅在宿主和用户允许时使用子代理，不自行开新聊天或改装多智能体框架。
3. 返回后查看真实输出、检查范围、问题和限制，再决定接收、最小修复、换层次或停止。工具校验成功只证明所检查的一致性；科学就绪仍依赖专业论证，不能从空目录、归档 complete、任务 completed 或退出码推断。
4. 一个故障先选当前主路由及依赖顺序。分析错误先修分析；执行故障先修执行；缺对照/可判别性回设计；有效证据挑战研究前提再回想法与相关文献。复核图文问题时也按根因处理。具体标准见路由参考。
5. 真正关闭本轮验收点后，更新工作状态并用 light-memory 保存值得保留的决定、依据、教训或限制。不要只交计划或一个 handoff 就声称完成已获授权的后续工作；后续超出请求时，完成当前范围并交具体可接续材料。

## 不丢失版本与运行身份

冻结设计不原地改；设计实质变化用新版本，批次保留所用设计与执行范围。失败重试新 run，保留父运行和成本，不增加独立样本量。新分析与评审轮次关联旧版本；同一篇核心稿件保留被审版本与修订版本。分析 handoff 是修订 brief，不能伪装成 design/idea 已支持的机器输入。

中断恢复先查正在运行、可能已完成或状态不明的 native run/job；确认前不重复启动、回滚或解锁。不确定终止状态需要专业恢复流程，不能简单把 Workflow 改成 pending 就重跑。`recovery_required` 保留曾启动后受阻任务的实际运行入口；更换目标、宣称本轮完成或替换该任务之前，先完成真实查证。更换输入版本或发现旧结果失效时，保留旧任务并创建有理由的后继；检查受影响的分析、图、文字、审稿结论和记忆。

## 本轮结束的依据

本轮交付达到约定、有效阴性已经回答问题、进一步行动不能消除关键不确定性、实际预算耗尽或必要条件缺失，均可构成结束/暂缓依据。不要为了正结果、更多实验或“流程完整”继续投入。相同解释反复失败且没有新增信息时，先核查历史与边际价值；循环上限按实际任务设置，不统一写死轮数。

准备送审的范围，区分科学充分性与投稿材料就绪；审稿意见 addressed 不等于 verified。选刊建议不自动成为作者决定。专利、软著以及期刊要求的当前规定在实际涉及时由相应技能核验；本技能不设立对所有研究一概适用的额外审核门槛。对外消息、投稿、申请、发布按用户真实授权处理。

## 可选的本地工作流工具

多步骤工作使用 `Workflow/workflow.json` 保留本轮目标、任务、依赖、实际文件指纹、状态变更和请求身份；`00-Workflow总览.md` 可重建。README/project.json 管导航，Memory 管研究记忆，专业阶段管事实，Workflow 管工作交接。简单工作不用建台账。

Python 3.10+ 标准库，台账独立运行；只读 resume 在 Memory 已存在时按需调用实际安装的 light-memory，不依赖模型 API、数据库或常驻进程。命令以本技能绝对目录替换 `<skill-root>`；使用前按需读 [台账契约](references/artifact-contract.md)。

```text
python "<skill-root>/scripts/leader.py" catalog --skills-root "<实际技能根目录>"
python "<skill-root>/scripts/leader.py" init --project "<project>" --spec "<实际目标.json>"
python "<skill-root>/scripts/leader.py" status --project "<project>"
python "<skill-root>/scripts/leader.py" resume --project "<project>" --query "本轮要解决的问题"
python "<skill-root>/scripts/leader.py" next --project "<project>"
python "<skill-root>/scripts/leader.py" apply --project "<project>" --spec "<实际变更.json>"
python "<skill-root>/scripts/leader.py" verify --project "<project>"
```

`next` 只筛选文件、依赖及台账预算符合条件的计划任务，由宿主选择科学路线并实际调用。脚本不读懂论文、不启动实验、不替代专业验收；运行中的记录不会自行推进。`init/apply --dry-run` 不写项目。请求可重试，修订号防止旧计划覆盖新计划，但不能保证外部任务恰好执行一次。

`resume` 同时给出 Workflow、候选和实际读取的 Memory context；缺任一入口仍可恢复另一侧。Memory 的冲突/失效/关闭依据变动不能因候选存在就忽略。reader_unavailable/read_failed 不是空记忆，先定位读取入口或从原生证据恢复。独立安装可传 `--memory-skill "<实际 light-memory 目录>"`；脚本不执行项目材料中的命令，也不把读取成功当作后台续跑。

## 交付

简洁说明本轮实际完成的成果与路径、关键结论和边界、仍在运行/受阻的工作、下一步及理由；区分本轮完成与整个科研问题解决。具体材料落盘后再报告，不能宣称自动续跑或后台监控。设计来源、学习路线见 [参考仓库与取舍](references/source-notes.md)，验证覆盖见 [验证记录](evaluations/verification.md)。
