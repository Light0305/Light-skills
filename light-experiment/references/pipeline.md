# 与 light-design 的交接

## 读取顺序与职责

先读项目的 `plan.md` 理解科学问题，再读 `design.json` 确认身份、执行范围和关系；`context.json` 只提供上游索引，引用论文存在不代表本轮已读。按需读取 protocols。调用上游 `design_bridge.py verify` 有助于检查原始设计，缺少该脚本时按已提供的契约核对，不要求安装上游技能。

用户交付目录通常是研究项目的 `Design/PROT-0001_方案短名/v01/`，已有方案按真实路径兼容；上游源码从当前安装位置查找。不要导入技能根目录的空白模板冒充用户方案。

| 上游字段 | 执行时的含义 |
|---|---|
| `selection.idea_id / idea_version`、`design_id / version` | 冻结并传递到所有运行，重设计创建新版本/执行批次 |
| `claims / experiments[].claim_ids` | 运行结果回答哪个有限主张；不把一次技术成功升级为主张成立 |
| `status / execution_scope` | 当前就绪的范围；执行请求不能使范围外实验自动就绪 |
| `resources / gates` | 本轮重新确认可用性；网页地址不等于已下载数据或已获得 GPU |
| `tasks / depends_on` | 先完成依赖并验收，未实现的 action 是开发任务，不是已有命令 |
| `units / allocation / sample_size` | 冻结单位、分配和重复，实际运行账本与之对账 |
| `procedure / measurement / analysis / decisions` | 实现与验收基准，改动需说明影响和是否已经看过结果 |
| `budget / constraints / history` | 实际运行限额、估算依据与历史变更，不凭空换算精确费用 |

导入可以接收 `draft / needs_input / hold`，但工具只允许在就绪状态且范围完整时准备正式运行。检查依赖是否跨出当前范围、是否有环。`ready_for_pilot` 的待确认后续阶段不阻断合法 pilot；pilot 成功也不自动授权后续阶段。

## 现有 brief 和临时实现

没有 JSON 的项目不需要为了执行一个已有命令制造大量表格。冻结用户已给的目标和配置，明确本轮可运行范围及限额即可；可手动按本技能的记录原则执行。若希望使用附带工具，先由宿主将 brief 映射为最小真实设计，并提供对应 `context / plan / design`，不要生成空字段只为让校验通过。

区分三个对象：`experiment_id` 是科学比较/实验包；`task_id` 是实现/运行/评价任务；`run_id` 是一次具体尝试。同一任务可有多个 seed 或实例，也可有失败重试。记录 `unit_id / seed / fold / instance / resolution` 等轴，重试用 `parent_run_id` 连接，而非增加科学样本数。

## 版本和偏离

输入快照一经用于运行即保持。原设计更新后，旧执行批次仍能通过本地快照复核；显示“上游已变化”，不改写旧版本。使用新设计时新建执行批次，交叉链接旧批次与修订说明。

Design 的本地来源核查与所选证据绑定由上游完整检查和宿主负责；Experiment init 不调用该检查，也不复制所有外部论文或数据。需要实际影响计算的文件必须在 run spec 中列明。当前就绪范围要求非空冻结正文；有内容不代表科学内容完整。

| 变化 | 处理 |
|---|---|
| 修复路径或日志缺失，不改变计算/评价语义 | 新 run，连接失败尝试，保留差异和验收 |
| OOM 后改变 batch/精度、求解器、截断或并行归约 | 判断是否改变比较/数值行为；必要时重跑匹配基线，说明偏离 |
| 修改终点、数据划分、排除规则、样本/任务集合或推断 | 返回设计修订；已看结果的修订不得标为预先指定 |
| 换数据/降规模才能跑 | 可作为明确标记的 pilot；不能声称原设计完成 |

只在用户要求或现有授权包含执行时启动研究任务。通常的“按这个方案跑完、记录结果”已经授权实现与预算内执行，不逐步重复询问。新增付费服务、外部发布或超出已知硬限额不属于默认扩展。

完成或更正后按 [原始证据与分析交接](evidence-and-handoff.md) 回传当前评估、失效依赖和实际原始文件。失败诊断、设计修订和科学前提改变返回不同层次；Memory/Workflow 用专业来源恢复与更新，不自动触发范围外运行。
