# 申请字段与单一事实源

这里是可复制填报底稿，不是中国版权保护中心的正式申请表。字段名、选项、字符计数、条件
必填及签章承诺须以实际办理页面为准；不要复刻一张看似官方、实际不可提交的自制表。

## 信息从哪里来

| 字段 | 可先整理的证据 | 仍需确认的部分 |
|---|---|---|
| 软件全称、简称、版本号 | 既有申请、发布包、版本配置、产品界面 | 本次登记名称和版本；不能自动把 0.x 改成 V1.0 |
| 著作权人及主体类型 | 用户提供的身份/主体材料、协议 | 准确名称、共同权利人、是否与开发者不同 |
| 开发方式 | 团队说明、合同、项目任务 | 独立/合作/委托/下达任务的真实关系；多人参与不自动等于合作开发 |
| 权利取得、权利范围 | 合同、转让/继承/授权依据 | 原始/继受、全部/部分以及支持材料；不能按代码作者自动判定 |
| 开发完成日期 | 版本记录、测试/交付材料作为辅助 | 实际完成时间；提交记录或文件创建时间不能直接替代 |
| 发表状态、首次发表日期/地点 | 对外发布记录作为辅助 | 用户真实发表事实；公开仓库日期不必然是首次发表日期 |
| 开发硬件/系统/工具 | 说明、环境锁定、配置、用户设备信息 | 实际开发条件；框架依赖不等于 IDE，不能虚构“Windows 11 + i7” |
| 运行硬件/系统/支撑环境 | 部署配置、实际运行、最低依赖 | 已验证与建议最低配置应分开；客户端与服务器分别写 |
| 编程语言 | 本次范围的实际实现 | 扩展名统计只是线索；不把 JSON 数据和文档语言全算进去 |
| 源程序量 | 冻结完整底稿的统计 | 统计口径和范围；不是节选后的 3,000 行，不包含外部依赖虚增 |
| 开发目的、行业、主要功能、技术特点 | 项目证据与用户业务说明 | 超出实现或证据的主张；不写无依据的性能、准确率或市场优势 |

证件号、联系地址、电话等只在任务确需时处理；不输出在研究报告或测试夹具中。
支持材料清单可写“身份证明/合同待提供”，草稿不必为了继续写作索要证件原图。

## 写法

- **开发目的**：谁在什么场景处理什么任务，这个软件提供什么处理能力。
- **主要功能**：沿实际流程说明输入、检查、处理、结果、查询/导出与必要管理能力。
  正文长度按当前字段约束组织，不靠重复句子填足字数。
- **技术特点**：只写实现中确有的处理机制，如流式读入、分块计算、断点恢复、权限校验；
  用机制和边界代替“先进、高效、行业领先”。没有测试依据不写倍率和精度。
- **环境**：准确列系统、解释器/运行时、数据库/中间件与关键依赖；不照抄整个依赖锁文件。

全称与版本在底稿中分开保存，材料标题用 `<全称> <版本>`。如果用户正式全称本身含版本文字，
按原字段保留并避免显示重复；不替用户改法定名称。所有材料沿用相同空格、大小写与版本写法。
遇到旧截图品牌/版权头，不直接删除：核对版本关系、权利边界和必要说明。

## 条件检查

- 发表状态为“未发表”，首次发表日期不随手填开发完成日期。
- 选择已发表，应核对日期、地点与完成时间关系；冲突先问事实而非自动修正日期。
- 合作/委托/任务/继受/修改开发：列适用协议、任务书、许可或权利取得证明缺口。
- 统计报告同时给原始物理行、非空程序行、底稿页数和拟提交页数；申请表按当前口径取值。
- UI 声明、日志和框架许可证中的署名与申请人不同，作为来源核对线索，不能直接删除解决。
- 当前字段字数/枚举核验不到时保留“待提交当日核验”，不套用网上旧版的固定上限。

`case.json` 中的 `reviews` 保存已确认事实及依据，`rules` 保存当次规则核验。
不要把 Agent 的“我认为没问题”登记成申请人已确认或登记机关已认可。
