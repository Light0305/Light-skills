# 检查现有材料与处理补正

## 先确定问题，不重新做整包

读用户提供的通知原文、现有表单、说明书、源程序和版本信息。补正通知可包含个人信息，
报告只引必要内容。对每项要求建立“通知内容—涉及文件/页码—冲突事实—修订动作—核验结果”。
通知不清楚时先解释能够判断的部分，只询问影响修订的事实。

## 核验顺序

1. **身份与事实**：名称/版本/权利人、开发方式、完成/发表状态和权利来源是否冲突。
2. **材料对应**：主要功能、文档章节、源码实现和截图是否描述同一版本/软件。
3. **完整程序范围**：源码行数是否来自完整范围，第三方/数据/生成物是否混入，是否用代码节选
   反推完整统计；来源不明时不能声称原创。
4. **连续与排版**：实际提交页数、前后连续关系、行数、真实结尾、A4、可读性和名称版本。
5. **证明与动态表单**：适用的协议/许可、主体材料、当前字段与签章。没有原件不模拟签章。

把发现分为“已核实问题”“需要申请人确认的事实”“办理口径待核实”“仅建议改善”。
可自动修的排版/同步/导出问题直接修；权属、日期和真实业务范围不能靠改词掩盖。

## 修改与回归

从 `case.json` 修唯一事实，再重建依赖材料。源码变动先重扫，保留 selection 中仍有效的
范围判断，审核新增/改动/删除项后再抽取。不能把过期 snapshot_sha256 手改成新值绕过审核。
补图核对图片版本、对应章节和说明，更新输入哈希；检查结果不变的文件无需重做。

复查修改处及关联字段，保留原始材料/通知和当前可上传文件的清单。补正说明仅在用户需要时
提供，应写具体修订事实和对应页码，不编造审查沟通结果，也不保证下次必然通过。

## 审查报告应可操作

每个问题给材料定位、实际不一致内容、影响和最小修法。不要只输出“命名须一致”等通用清单。
本地 `audit.json` 只是机器检查结果；其“权属审核已填”“视觉核验已记录”仅代表有人留下了
依据字段，不代表工具已经验证事实真实性或替代专业判断。

外部正式提交需明确用户指令，且只能按当时可用的官方流程办理。本 skill 的脚本不登录、不上传、
不签章、不创建申请。用户只让准备材料时，在可审阅本地结果完成后交付即可。
